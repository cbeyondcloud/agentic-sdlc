# M3 Load test Implementation Plan (M3-22)

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Show that one control plane serves 1000 concurrent runs. A load harness simulates N runs spread over tenants and teams. Each run speaks the real CLI protocol: it follows the active policy, registers, beats on the policy's interval, polls the kill switch on the CLI's cache interval with its ETag, and posts chained event batches as the CLI's background sink does. The events are a recorded feature-delivery ledger, re-chained per run with the ledger's own hash. The harness measures ingest lag end to end (event produced -> committed and seen by a separate database reader), latency per route, errors by status, database connections, and CPU and memory of the API and Postgres containers. We run it once at 1000 runs on this laptop, fix the bottlenecks that are in our code (test first), and write a report. A 20-run smoke version runs in `check.py` so the harness keeps working.

**Architecture:**
- **Harness (`control-plane/loadtest/`, not a shipped package).** `cp_loadtest/` holds the modules; `loadtest.py` is the entry point (`uv run python control-plane/loadtest/loadtest.py up|run|down`). It is not one of the import-linter root packages: it may import `agentic`, `agentic_cli` (client constants and the sink's chunking) and `agentic_cp` (seeding).
  - `profile.py`: the run profile read from `fixtures/feature-delivery.events.jsonl` (a real 40-event ledger of the M1-68 acceptance run: 14 step executions, 4 gate waits - one rejection -, 2 loop-backs) and `Timing` (step, gate, heartbeat and kill-poll seconds, with jitter). `plan_run()` turns the profile into timed actions: produce an event, pause at a gate (the CLI exits), resume.
  - `chain.py`: `RunChain` re-chains the template entries for a new run id, team and policy version: `seq`, `prev`, `at` and `hash` = `sdlc_commons.ledger.entry_hash` (Zyroflo's formula). A test proves the result passes `verify_entries` and equals what `RunLedger` would accept.
  - `wire.py`: `Wire`, an async client on `httpx2.AsyncClient` that sends exactly what `ControlPlaneClient` sends (paths, headers, JSON bodies built from `agentic.orgapi` models, the kill poll's `If-None-Match`, timeouts and the 429 rules from `agentic_cli.control_plane`). A contract test captures both clients' requests and compares them.
  - `sim.py`: `SimulatedRun`, one asyncio task per run: init on a user's first run (`/me`, `/policy/active`, bundle with digest check), then per run `/policy/active` + `POST /runs`, heartbeat loop, kill-poll loop (10 s, ETag), event production, and a sink task that sends every pending entry in chunks from `ControlPlaneSink._chunk` (at least once, `ingest.gap` catch-up from the server's head). A closed run is replaced by a new one, so N stay open.
  - `stats.py`: `Recorder` (per route latency, status counts, transport errors, lag samples), percentiles, the summary and the target verdicts.
  - `observe.py`: `HeadWatcher` (a superuser connection reads `runs.head_seq` every 250 ms: the time an event became visible), `DbSampler` (`pg_stat_activity` by state and wait type), `ContainerSampler` (`docker stats`), `LoopLag` (the driver's own event-loop delay, to prove the driver was not the bottleneck).
  - `seed.py`: tenants, teams, users and tokens (the control plane's own functions on the owner role), the policy repo (standalone template + the library's feature-delivery pipeline + one team file per team) synced through `bootstrap_tenant`, and role assignments through `POST /v1/rbac/import` (timed: DF-569).
  - `stack.py` + `compose.yml`: the target. Project `agentic-m3-load-test`: `lt-postgres` (the pinned `postgres:17.10-alpine`, 2 CPU / 4 GB, fsync on), `lt-init` (migrate, grant-runtime), `lt-cp-1` and `lt-cp-2` (the control-plane image built from `control-plane/Dockerfile`, 1 CPU / 1 GB each, as the master plan's "2-3 replicas x 1 vCPU / 1 GB"), `lt-worker` (the background worker). Ports bind to 127.0.0.1 on random host ports. Runs are spread over the replicas by run (what a Kubernetes Service does per connection).
- **Fixes in `agentic_cp`.** Only for bottlenecks the 1000-run test shows, each with a failing test first. Candidates from reading the code: the hard-wired pool (`pool_size=5`, overflow 10) for three transactions per request; `touch_token`'s transaction on every request; the per-tenant registration lock and its two counts.
- **Smoke (`control-plane/tests/test_loadtest_smoke.py`).** 20 runs for 30 s with compressed timing, against the app under uvicorn in a thread on the test Postgres (`pg_server`: a container, or `AGENTIC_CP_TEST_DSN` on Linux CI). Generous thresholds. Skips with the database fixture's reason when there is no container engine.

**Tech Stack:** Python 3.12 asyncio, `httpx2` (existing), `asyncpg` (existing), stdlib `statistics`, Docker or Podman compose. No new dependency.

**Spec:** `docs/superpowers/specs/2026-10-16-agentic-sdlc-design.md` "Sizing"; master plan "Sizing" and row M3-22 ("1000 concurrent runs reporting to control plane; ingest lag and error targets met"; acceptance "p95 ingest lag and error rate within targets; sizing updated").

## OSS reuse decisions

| Need | Reused | Not reused, why |
|---|---|---|
| Load driver | asyncio + `httpx2.AsyncClient` (already a dependency) | Locust (MIT): gevent monkey-patching fights asyncio and asyncpg (the head watcher), adds gevent/greenlet/Flask, and still needs our own chain building and lag measurement. k6 (AGPL) not allowed. Vegeta (MIT), oha (MIT), wrk (Apache): native binaries, not allowed on this Windows machine, and fixed-rate request blasters, not stateful run simulations |
| Request shapes | `agentic.orgapi` models, `agentic_cli.control_plane` constants and `ControlPlaneSink._chunk` | a second hand-written protocol |
| Chained batches | `sdlc_commons.ledger.entry_hash` / `verify_entries` (Zyroflo's formula) | made-up events |
| Percentiles | stdlib `statistics.quantiles` | HdrHistogram ports: more than a few hundred thousand samples need |
| Container metrics | `docker stats` / `podman stats` CLI | cAdvisor, Prometheus: a monitoring stack for one laptop run |

## Global Constraints

- **Real protocol only.** Every request the driver sends is one the CLI sends, with the CLI's headers. The contract test fails when `ControlPlaneClient` changes a shape.
- **Lag is end to end.** Produced = the moment the simulated CLI appends the event to its chain. Committed = the ingest response that carried it returned 2xx (so client queueing, 429 waits and gap catch-ups count). Visible = the head watcher's first read with `head_seq >= seq`. Both are reported; the target is on visible.
- **Errors.** A transport error, a timeout, any 5xx, a 429 and any 4xx except the kill poll's 304 count as errors. Rate = errors / requests.
- **Names.** Containers, the compose project and the image carry `m3-load-test`; `down` removes only those (by project), never anything by image name.
- **Cross-platform.** The harness runs on Windows (PowerShell) and macOS/Linux (bash/zsh) with Docker or Podman (`CONTAINER_ENGINE`), paths via `pathlib`, files written with `newline="\n"`.
- **Secrets.** The stack's database passwords are random per `up`, kept in the git-ignored `control-plane/loadtest/.state/` and never printed; tokens stay in memory.
- **Indicative.** The full run is on one Windows laptop whose Docker VM (6 CPU, 16 GB) also runs other projects' containers. The report says so and lists what to re-run on staging.
- **Formatting, CI and records:** never add `# fmt: skip` / `# fmt: off`; line length 100; check pytest's exit code directly; `uv run python scripts/check.py --all` green; TRACKER.md, DEFERRED.md and DECISIONS are updated by the coordinator from this track's output.

## Proposed targets (needs decision; defaults used)

At 1000 concurrent runs on the reference stack (2 replicas x 1 vCPU / 1 GB, Postgres 4 vCPU / 16 GB):

| Measure | Target | What fails when it is missed |
|---|---|---|
| Ingest lag (produced -> visible), p95 | <= 5 s | Dashboards, budget alerts at 80/100 % and gate-waiting mails arrive late; the stale-run sweep sees old `last_event_at` |
| Ingest lag, p99 | <= 15 s | As above for the slowest runs; a backlog that grows instead of draining |
| Error rate (all routes) | <= 0.1 % | Each failed ingest is retried (at least once, so no loss) but piles up in the offline queue; failed beats make live runs look stale (DF-769) |
| Kill-switch poll latency, p99 | < 2 s | The CLI waits 5 s at most; after 60 s without a confirmed answer runs pause ("unconfirmed"), and a kill takes longer than the 30 s target (M2-54) |
| Heartbeat latency, p99 | < 2 s | The beat times out at 5 s; missed beats free a live run's slot |
| Registration latency, p95 | <= 2 s | Every `agentic run` waits on it |

## Review Focus

1. **Protocol fidelity.** The driver's requests equal `ControlPlaneClient`'s (method, path, query, headers, body) for policy, registration, heartbeat, kill poll (with and without ETag) and ingest; chunking is `ControlPlaneSink._chunk`. Test: `test_wire_requests_equal_the_cli_client`.
2. **Chains verify.** A re-chained run passes `verify_entries`, keeps the template's event order and sizes, and a second run differs only in run id, times, identity and hashes. Tests: `test_chain_verifies_and_keeps_template_shape`.
3. **Lag is measured end to end.** The visible lag comes from a separate database reader, not from the HTTP response; a run whose ingest is refused and caught up still reports the true lag. Tests: `test_head_watcher_marks_visibility`, `test_sink_catches_up_after_gap`.
4. **Fixes are real and tested.** Each bottleneck fix has a test that fails before it (pool settings honoured; whatever the run shows), and the report shows before/after numbers.
5. **Nothing leaks.** `down` removes only the `agentic-m3-load-test` project; no secret is printed or committed; the smoke test leaves no container behind.
