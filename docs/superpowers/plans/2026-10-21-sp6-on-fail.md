# SP6 follow-up: route work back on a failing QA or review (DF-238)

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A run never ends `completed` while its newest QA or review handoff reports a failure (SP18b review F2, DF-238). In the library pipelines a failing QA routes the work back to the Developer automatically, bounded by the loop's `max_iterations`; an exhausted loop waits at its gate (exit 4) and a person can no longer wave it through as it stands; any other pipeline that would end with a failing handoff pauses `failing-handoff` (exit 4) instead of completing.

**Rows:** M1-24 follow-up (loops), M1-61 follow-up (library pipelines). Closes DF-238 (target M1-68).

**Architecture:** no new pipeline syntax. The existing model already has the route back: a loop repeats its body until `until` holds. Two small engine rules make the loop's exit condition binding, and one completion rule covers pipelines without such a loop.

- **Library pipelines (the route back).** QA moves inside the build loop, after review, guarded by `when: "review.open_blocking == 0"` (QA runs only on a change the reviewer passed). The loop's `until` becomes `review.open_blocking == 0 && test_report.verdict == 'pass'`. A QA `fail` therefore loops back to `develop`, whose inputs already include the newest `test-report` (the QA report naming the failures). CEL's `&&` absorbs an error on the right when the left is false, and QA always runs when review passes, so the baseline's `test-report` never decides the loop. The `review-approval` gate moves after the loop: a person reads the change together with its QA report before the PR.
- **Engine rule 1: an exhausted loop is not approved as it stands.** At `<loop>-exhausted`, `approve` is refused while the loop's `until` is still false. The person edits a pinned handoff so that it holds (marking a finding `accepted`, listing a pre-existing failure in `baseline_failures` - an attributable, digest-pinned attestation), rejects with feedback (another pass of the loop) or stops the run (exit 5). `edit` re-evaluates `until` on the edited handoff.
- **Engine rule 2: completion requires no failing handoff.** Before the engine closes a run `completed`, it asks each newest handoff (`state.latest`) whether it reports a failure: `HandoffBase.failure()` returns `None`; `ReviewData` reports open blocking findings, `TestReportData` a `fail` verdict (extensions inherit it, D37). Any failure pauses the run `failing-handoff` with the reasons; `resume` re-checks, `stop` ends it.
- **CLI.** `next_steps` for `failing-handoff` offers `show` and `stop` (resume would only pause again); exit code stays 4 (paused, waiting for a person).

**Tech Stack:** Python 3.12, cel-python (already used), pydantic, pytest with pydantic-ai `FunctionModel` fakes.

**Spec:** §6 (pipelines, `when`/`until`, gate decisions), §6.2 (library pipelines), §8.3 (gates persist and exit), §8.7.

## Rulings (recorded for the owner)

1. **Loop-until over QA, not gate `when` or an `on_fail` route.** It reuses the bounded loop, its oscillation check and its exhaustion gate; pipeline files stay valid (no new keys). Gate `when` needs a person for every QA failure and gives `approve` no safe meaning; `on_fail` would add a second, differently bounded back edge next to loops (D3: linear + gates + bounded loops).
2. **Exhausted loops can no longer be approved as they stand.** Accepting a failure is an `edit` of the handoff (attributable, pinned) rather than a bare approval. Behaviour change for every `on_exhausted: gate` loop; no existing test or pipeline relied on bare approval.
3. **Completion backstop is a pause (`failing-handoff`), not `failed`.** Exit 4, keeps the run inspectable, and it is the "needs attention" outcome the brief asks for; `failed` would exit 1.

## Final review fixes (F1-F3)

The final review (Sonnet 5.5, 8192a25..4c7b381) found three Important problems; each is
fixed with a regression test seen red, then green.

- **F1: the loop could end on a report QA never wrote.** With QA guarded by
  `when: review.open_blocking == 0`, a review that blocked every round left the intake
  baseline's `pass` as the newest test report; a person accepting the review's findings
  at the exhausted gate then ended the loop, and the PR opened, with QA never run. Fix:
  QA runs in every round (no `when`), so the loop always ends on QA's report about the
  current change; this supersedes the "QA always runs when review passes" assumption in
  the Architecture above. Cost: one QA step per round while review still blocks (the
  Developer then gets both reports at once). Tests:
  `test_accepting_the_review_never_ends_the_loop_on_a_stale_test_report`,
  `test_accepting_the_review_ends_the_loop_on_this_rounds_qa_report`.
- **F2: a non-blocking finding left open read as oscillation.** `_open_issues` now counts
  only open findings at a blocking severity (the run's `block_on`), the ones that decide
  the loop. Test: `test_a_non_blocking_finding_left_open_is_not_oscillation`.
- **F3: accepting a QA failure meant falsifying the report.** `test-report` gains
  `accepted_failures` (failing tests or criterion ids a person accepted at a gate): a
  `pass` may carry a failure named there, the report keeps saying it failed, and
  `baseline_failures` stays the intake truth. Like accepting a blocking finding (DF-41),
  only a person may write it: `finalise_handoff` refuses it from an agent. The refusal at
  the exhausted gate and the CLI hint say how. Tests:
  `test_a_pass_may_carry_failures_a_person_accepted`,
  `test_a_pass_with_a_failure_nobody_accepted_is_still_invalid`,
  `test_an_agent_cannot_accept_a_failing_test`,
  `test_a_person_accepts_a_qa_failure_without_rewriting_history`, and the CLI hint test.
