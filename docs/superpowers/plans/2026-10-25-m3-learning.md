# M3 Learning loop L1-L3 Implementation Plan (M3-11, M3-12, M3-13)

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Every human correction of an agent's work becomes a feedback record (L1), each record is attributed to the agent(s) that should learn from it (L2), and repeated similar corrections become a learning *proposal* (L3). Four signals are captured: a gate rejection with feedback, a gate edit (the diff between the agent's handoff and the person's edit), a review comment or "changes requested" on an agent-made pull request, and a review-agent miss (a person asks for a change on lines the Code Review agent passed). Records are kept in the run folder (a hash-chained feedback journal next to the run ledger) and are delivered to the control plane by the existing sink machinery, per tenant, under forced RLS, visible to their author and to the team (D30). Attribution is rules first, then the built-in **Learning Analyst** agent with a confidence; a person can correct it (CLI and control-plane endpoint, audited). Lessons cluster per agent and scope with a deterministic similarity method; a cluster becomes a proposal at the policy threshold (default 3 similar corrections in 30 days); a rejected lesson is not proposed again until new evidence reaches the threshold. Proposals are only **created** here: nothing applies them (L4-L6 are M3-14..16), so no skill, memory or agent changes (D29).

**Architecture:**
- **Zyroflo reuse (`sdlc_commons.feedback`).** The feedback journal is Zyroflo's run-folder `feedback.jsonl` (`tools.sdlc.feedback.append` / `read` / `path_of`): its locked, newline-safe append and its de-duplication by row `id`. The adapter adds what Zyroflo's file lacks for our use: each row we write is chained (`seq`, `prev`, `hash` = Zyroflo's `entry_hash`), so the control plane verifies it like the run ledger and the personal-backup journal. Zyroflo rows of its own kinds in the same file are ignored by our reader. Zyroflo `learning.py` (review-suppress proposals with corpus gate, apply and undo) is the L4-L6 shape and is not used here; its gaps are recorded for those rows.
- **New core package `agentic.learning`** (imports neither `sdlc_commons` nor Zyroflo):
  - `records.py`: `FeedbackRecord` (one correction), `Learner`, `Attribution`, the journal event names and payload builders, and `fold(entries)` (the current state of each record: record, attribution, lesson).
  - `capture.py`: builders, one per signal: `gate_rejection`, `gate_edit` (unified diff by `difflib`), `pr_feedback` (reviews and inline comments of an agent-made pull request), `review_misses` (inline change requests on lines with no Code Review finding).
  - `attribution.py`: the rules table (spec §24 "Attribute").
  - `analyst.py`: the Learning Analyst port: `AnalystContract` (an `OutputContract` that accepts one JSON verdict), `LearningAnalyst` (runs the library agent through any `AgentRunner`), `analyse(record, rules, analyst)`.
  - `lessons.py`: deterministic lesson normalisation (fallback when no model is used), tokenising, the `Similarity` port with the default `LexicalSimilarity` (Dice over stemmed content words) and an optional `EmbeddingSimilarity` behind an `Embedder` port (off by default; nothing wires a model to it).
  - `clustering.py`: `propose(lessons, settings, now, pending, rejected)`: clusters per agent and scope, threshold and window, narrowest scope (repo, then team across repos), rejected-lesson memory.
  - `store.py`: `LocalLearningStore`: proposals and rejections in `.agentic/local/learning/` (standalone).
- **Policy (`agentic.policy.model`).** `OrgPolicy.learning: LearningPolicy` (threshold 3, window_days 30, similarity 0.5) and `TeamPolicy.learning: TeamLearning` that may only tighten (a higher threshold, a shorter window).
- **Engine.** An optional `feedback` port (`Callable[[FeedbackRecord], None]`). On a rejection the engine builds a `gate-rejection` record for each pinned handoff's agent; on an edit-and-approve, a `gate-edit` record with the diff. A failing port is logged and never stops the decision (the gate ledger already holds it).
- **GitHub adapter.** `FeedbackHost` protocol (vendor-neutral) with `pull_request_reviews` and `pull_request_review_comments`; `GitHubHost` implements both. Tests serve recorded GitHub API fixtures (JSON files) through `httpx2.MockTransport`.
- **Built-in Learning Analyst.** `library/agents/learning-analyst.md` of a new org agent type `learning-analyst` (tier `fast`, no tools, no handoff), added to both policy templates. Tested with `TestModel` / `FunctionModel` only.
- **CLI (`agentic learn`, new command module).** `feedback` (list a run's or every run's records), `capture-pr <run>` (read the run's pull request reviews through the configured host and record `pr-review` and `review-miss` records), `analyse [<run>]` (run the Learning Analyst on records not analysed yet), `attribute <feedback-id> --agent A [--agent B] --reason T` (a person's correction: the control-plane endpoint in org mode, the run's journal standalone), `proposals` (the proposals created so far; standalone recomputes them). The engine port is wired to the run's journal; each journal write is forwarded by `FeedbackSink` (a `ControlPlaneSink` to `/v1/runs/{run}/feedback`) with `agentic.telemetry.sinks.forward` and its cursor, screened by the publish scan first.
- **Control plane.** Migration `m3_11_learning` (after `m2_09_routing`): `feedback_events` (insert-only evidence: each run's journal entries as received), `feedback` (one row per record: attribution, lesson, author, team, repo), `learning_proposals`. All three under forced RLS with isolation factories. Routes: `POST /v1/runs/{run_id}/feedback` (ingest: verified chain, all or nothing, replays are duplicates), `GET /v1/learning/feedback`, `PUT /v1/learning/feedback/{feedback_id}/attribution`, `GET /v1/learning/proposals`. Ingest folds the entries into `feedback` and re-clusters the affected agent and team with the run's policy version `run_settings["learning"]`; each stored record, correction and new proposal is on the tenant's audit chain (`learning.feedback_captured`, `learning.attribution_corrected`, `learning.proposed`).

**Tech Stack:** Python 3.12, stdlib `difflib` (diffs), Pydantic v2, Pydantic AI (existing; the analyst runs through `PydanticAIRunner`), FastAPI + SQLAlchemy Core + Alembic (existing). No new dependency.

**Spec:** `docs/superpowers/specs/2026-10-16-agentic-sdlc-design.md` §24 "Learning loop" (D29), §23 ownership (D30). Master plan "Learning loop", rows M3-11..M3-13. Deferred register: DF-290 (failing CI logs, targeted "M3-11 or a later GitHub row").

## OSS reuse decisions

| Need | Reused | Not reused, why |
|---|---|---|
| Feedback record file in the run folder | Zyroflo `tools.sdlc.feedback` `append` / `read` / `path_of` via `sdlc_commons.feedback` | Zyroflo `feedback.capture` is bound to its own gate flow (`state.json`, `reviews.jsonl`) and record kinds; our engine records gates with `approve.append_entry` |
| Chain hash | Zyroflo `approve.entry_hash` via `sdlc_commons.ledger.entry_hash` | — |
| Repeated-correction proposals | the idea of Zyroflo `feedback.group_corrections` (lexical, distinct evidence, stable order) | it groups by exact finding id over `reviews.jsonl`; our lessons are free text per agent and scope. Zyroflo `learning.py` is apply/undo for review suppressions: an L6 input |
| Text similarity | stdlib only (token Dice, small stemmer) | rapidfuzz (MIT) and datasketch (MIT) are more than a few-hundred-lesson cluster needs and add a native or numpy dependency; scikit-learn is far heavier. An embedding model stays optional behind a port |
| Diffs | stdlib `difflib.unified_diff` | — |
| Analyst | Pydantic AI through the existing `PydanticAIRunner` (budget, stuck check, output retry) | a second agent loop |

## Global Constraints

- **Nothing is applied.** No code in this plan writes a skill, a memory file, AGENTS.md or an agent definition. A proposal is a row (control plane) or a JSON line (`.agentic/local/learning/proposals.jsonl`) with status `pending` or `rejected`.
- **Ids.** A feedback id is `fb-` + 20 hex of sha256 over `run_id`, the signal and its source key, so capturing the same correction twice records it once. A proposal id is `lp-` + 20 hex over agent, scope and the seed lesson's tokens.
- **Size caps.** Text 4 000 characters, diff 32 000 characters (cut with a marker), lesson 200 characters, at most 50 records per `capture-pr` call per pull request page set.
- **The journal holds prose; the run ledger never does.** The ledger's "ids only" rule stands; feedback text and diffs live only in the feedback journal and the control plane's `feedback` rows.
- **Publish scan.** In org mode each journal entry is screened (`PublishGuard.screen`) before it is chained and checked (`check`) before it is sent; the giver's identity travels in the `actor` field, which the scan treats as an identity field (as for `approver`).
- **Visibility (D30).** A feedback row is read by its author (the user whose CLI sent it) and by holders of `dashboard.view.team` in its team; another tenant's record is 404. A correction needs the author or `agent.approve.repo` in the team. Proposals are read by holders of `dashboard.view.team` in the team and by authors of their evidence.
- **Similarity is deterministic.** Same lessons in, same clusters and ids out, on Windows and Linux; no model is called by clustering.
- **No live model, provider, TokenLean or GitHub calls in tests** (owner decision 73): `TestModel`/`FunctionModel`, `httpx2.MockTransport` with recorded fixtures, the existing fake GitHub server.
- **Formatting, CI and records:** never add `# fmt: skip` / `# fmt: off`; line length 100; check pytest's exit code directly; `uv run python scripts/check.py --all` green on Windows and Linux; TRACKER.md, DEFERRED.md and DECISIONS are updated by the coordinator from this track's output.

## Review Focus

1. **The feedback journal chain and its delivery.** An entry edited, removed or reordered is refused by the control plane (422 `ingest.chain_broken`); a replayed batch is a no-op; a batch for a run this tenant does not hold is 404 (another tenant's run looks exactly like a missing one); the cursor moves only after acceptance. Tests: Task 1 `test_journal_chains_entries_and_verifies`, Task 10 `test_feedback_ingest_is_all_or_nothing_and_replay_safe`, `test_feedback_for_unknown_run_is_404`.
2. **One test per signal type** (row M3-11): `test_gate_rejection_becomes_a_feedback_record`, `test_gate_edit_records_the_diff`, `test_pr_review_comments_become_records`, `test_review_miss_on_lines_the_review_passed` (Tasks 2-5), and each reaches the control plane (`test_each_signal_reaches_the_control_plane`, Task 10).
3. **Attribution rules** (row M3-12): PR code comment -> Developer + Code Review; requirements edit -> Business Analyst; design reject / architecture comment -> Design; missing tests -> QA (+ Developer when TDD was skipped); a custom agent's handoff -> that agent; otherwise the Learning Analyst with a confidence (TestModel). A correction by someone who is neither the author nor holds `agent.approve.repo` is 403 and changes nothing; an allowed one is audited. Tests: Task 6, Task 7, Task 10 `test_attribution_correction_is_audited_and_permissioned`.
4. **Thresholds and rejected memory** (row M3-13): 2 similar -> no proposal, 3 -> one proposal; outside the window they do not count; a team may only tighten; a rejected lesson with 1-2 new similar corrections is not proposed again, with 3 new ones it is. Tests: Task 8.
5. **Isolation.** Every new table has a row factory (`test_tenant_isolation` runs every operation), every new route has an `EndpointCase`.
