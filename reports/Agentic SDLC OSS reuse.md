# Build the governed core, reuse everything else

No open-source project is worth adopting or forking as the whole framework. As of 16 October 2026, no single candidate covers even about 70% of the brief. The gaps are always the same four: a Python runtime where every model call goes through one proxy, an org > team/user > repo policy layer with admin override of model, provider, tools and spend, schema-validated Markdown handoffs, and multi-tenant operation for about 1,000 developers. The recommended route is a thin Python orchestration and governance core that you write yourselves. Underneath it sits **Pydantic AI v2** as the agent loop. Model calls use the native **openai/anthropic SDKs** with an injected `httpx` transport that stamps identity headers and harvests TokenLean cost headers. External coding agents (**Claude Agent SDK**, **`codex exec`**, and an **ACP** adapter for the long tail) plug in as backends. Each step runs in a **git worktree** of its own, with **Anthropic `srt`** or **Codex's native sandbox** around it. **code-review-graph** answers impact questions, **AGENTS.md** holds repo memory, and plain **OpenTelemetry** carries `traceparent` into TokenLean. **Archon v2** is the closest end-to-end match, and you should copy its pipeline node vocabulary, but it is TypeScript, routes calls through each coding harness rather than one base_url, enforces no budgets and has no org policy layer. The custom code that remains is mostly governance plumbing: the pipeline state machine, the layered-config merger with locked fields, preflight policy checks, handoff schema compatibility, child-agent budget slicing, the TokenLean transport and the backend adapters. TokenLean itself needs several upgrades, chiefly multi-format endpoints (Anthropic Messages and OpenAI Responses), cost reporting on streamed responses, `traceparent` extraction, a team scope with a remaining-budget API, and hierarchical budgets.

## No end-to-end framework clears 70% of the brief, and Archon comes closest

The first-generation "virtual software company" projects are dead ends. MetaGPT (MIT, 70.9k stars) has had only minor commits since mid-2025, and its last release dates from April 2024 ([MetaGPT](https://github.com/FoundationAgents/MetaGPT/commits/main)). ChatDev's classic software-company mode now lives on a legacy `chatdev1.0` branch after the project pivoted to the general-purpose "DevAll" platform ([ChatDev](https://github.com/OpenBMB/ChatDev)). GPT-Pilot is disqualified twice over. It uses the non-OSI Functional Source License, and its README carries a banner saying **a credential-stealing supply-chain worm sat in `core/telemetry/` from August 2025 until 11 June 2026** and that the repo "is no longer actively maintained" ([GPT-Pilot](https://github.com/Pythagora-io/gpt-pilot)). Devika calls itself experimental, and Devon is stale and AGPL-3.0 ([Devika](https://github.com/stitionai/devika), [Devon](https://github.com/entropy-research/Devon)). An independent June 2026 comparison of spec-kit, OpenSpec, BMAD, GSD, Spec Kitty and Reversa found that **no framework strongly covers all six process dimensions** and named "a structural trade-off between process depth and portability across agents" ([arXiv 2606.04967](https://arxiv.org/abs/2606.04967)).

The 2026 activity has moved to workflow engines that sit on top of coding harnesses, and **Archon v2** is structurally the closest of them. It defines development processes as YAML workflows with `prompt`, `bash`, `loop`, `approval` and `cancel` nodes, `when:` branching, and a `loop` that runs `until: ALL_TASKS_COMPLETE` with `fresh_context`. Its `loop_group` with `max_iterations: 5` wraps an approval form, so a reviewer rejection loops back to revision, which is exactly your review-loop pattern ([Archon README](https://github.com/coleam00/Archon)). Each node takes its own `model`, `provider`, `effort`, `allowed_tools`/`denied_tools` and `output_format`. It also has `small`/`medium`/`large` model tiers with aliases, worktree isolation by default with an optional container, a web UI, Slack and GitHub webhooks, and Postgres-backed users ([Archon docs](https://archon.diy/llms-small.txt)). On mechanics it is the right product. It fails the brief on everything around the mechanics. It is TypeScript/Bun. Its providers are agent harnesses (Claude Code, Codex, OpenCode, Copilot, Pi), and a custom OpenAI-compatible endpoint is documented only through Pi, with an OpenCode external `baseUrl` "not supported". Config layering stops at install-wide plus per-repo plus per-user, with **no org/admin policy layer**. `maxBudgetUsd` is "tracked but not enforced" for some providers ([Archon docs](https://archon.diy/llms-small.txt)). It also removed its legacy `archon-*` workflows between versions, and PostHog telemetry is on by default ([Archon README](https://github.com/coleam00/Archon)). Forking it would mean inheriting a fast-moving TypeScript codebase and then building the governance core inside it anyway.

The other serious candidates each cover one slice. **OpenHands** (MIT) has pivoted into "Agent Canvas", and its Python software-agent-sdk owns agents, tools, conversations and Docker/Kubernetes workspaces ([software-agent-sdk](https://github.com/OpenHands/software-agent-sdk)). Its file-based sub-agents are Markdown with YAML front matter carrying `tools`, `model: inherit`, `max_iteration_per_run`, `mcp_servers` and `permission_mode`, very close to your template ([OpenHands file-based agents](https://docs.openhands.dev/sdk/guides/agent-file-based)). It has no declarative role pipeline with gates or loops, though, and no org override layer. **spec-kit** (MIT, Python, 141.5k stars) has the best artefact chain. Its workflow engine supports `gate` with `on_reject`, `if`/`switch`, `while` and overlays that modify an installed workflow without forking it ([spec-kit workflows](https://github.github.io/spec-kit/reference/workflows.html)). But it relies on the host coding agent for every model call, and its `shell` steps run "with your privileges and has no sandbox". **BMAD** gives you rich personas and a precise base → team → user TOML merge, but it is a prompt methodology with no engine, its trademark notice covers "all casings and variations" of the name, and v7 is a breaking alpha ([BMAD LICENSE](https://github.com/bmad-code-org/BMAD-METHOD/blob/main/LICENSE), [BMAD README](https://github.com/bmad-code-org/BMAD-METHOD)). **Open SWE** looks like a "software factory", but it accepts no external contributions and "production standalone Agent Server deployments require a license key" ([Open SWE](https://github.com/langchain-ai/open-swe)). **ChatDev 2.0**, **Microsoft Agent Framework** and **crewAI Flows** all have graph engines with human nodes, but none is git- or PR-centric, and none has sandboxing or governance ([ChatDev workflow authoring](https://github.com/OpenBMB/ChatDev/blob/main/docs/user_guide/en/workflow_authoring.md), [Agent Framework](https://github.com/microsoft/agent-framework), [crewAI Flows](https://docs.crewai.com/en/concepts/flows)). **gh-aw** compiles Markdown + YAML agents into sandboxed GitHub Actions with validated "safe-outputs" for writes, which makes it a CI target rather than a pipeline engine ([gh-aw](https://github.com/github/gh-aw)).

| Disposition | Projects | Reason |
|---|---|---|
| Copy semantics, do not fork | Archon v2 | Its node model matches your DSL, but it is TypeScript, routed through harnesses, and has no org policy or enforced spend |
| Depend on as components | OpenHands SDK (stuck detector, optional Docker/K8s workspaces), gh-aw (CI target), container-use (container pattern) | Each solves one layer cleanly under a permissive licence |
| Borrow formats and ideas | spec-kit, OpenSpec, BMAD (renamed), goose recipes, ChatDev 2.0 YAML DAG, Open SWE layered MCP scope, Orchestrator.inc Kanban, wshobson/VoltAgent role prompts, Superpowers TDD discipline | Content and conventions, no runtime |
| Ignore | MetaGPT, ChatDev 1.0, GPT-Pilot, Devika, Devon, SWE-agent (superseded by mini-swe-agent), Agentless, AutoGen (maintenance mode), Aider as a framework, claude-task-master, claude-squad, Ruflo, small 2026 "agentic-SDLC" repos | Dormant, compromised, copyleft, non-OSI or immature |

The case for building rests on things nobody ships. The pipeline DSL already exists twice (Archon, spec-kit), so you should copy its semantics rather than invent them. Org-level admin override of model, provider, tools and spend is the clearest white space: no candidate offers it. One steelman for adoption deserves a fair hearing. A team willing to work in TypeScript could fork Archon and add a policy layer plus TokenLean routing, and would get a web UI and webhooks for free. That trade fails here because harness-mediated calls put enforcement outside the framework, Archon's churn would make a fork expensive to rebase, and the Python requirement is explicit.

## Recommended stack: your own pipeline outside, Pydantic AI inside

The pipeline model of linear steps, gates, bounded loops and conditional branches, with child agents instead of pipeline parallelism, is simple enough that **a graph engine adds little**. The reusable value lies in the inner agent loop: tool calling, provider adapters, structured-output validation, usage limits, HITL deferral and OTel. Pick the library on those grounds and hand-roll the step state machine against the run folder. The table below gives the full component map. The narrative after it explains the non-obvious choices.

### The core engine: Pydantic AI for the loop, a run folder for state

**Pydantic AI v2** fits the inner loop best because its strengths line up with your requirements. Its declarative AgentSpec in YAML or JSON carries `instructions`, `model`, `model_settings`, `output_schema` and `retries`, which gives your plain-English templates a compile target ([Agent spec docs](https://pydantic.dev/docs/ai/core-concepts/agent-spec/)). `ModelSettings.extra_headers` works across OpenAI, Anthropic, Google, Bedrock, OpenRouter and Ollama adapters ([settings.py](https://github.com/pydantic/pydantic-ai/blob/main/pydantic_ai_slim/pydantic_ai/settings.py)). `UsageLimits` caps requests, tool calls, tokens and cost ([Agent docs](https://pydantic.dev/docs/ai/core-concepts/agent/)). A tool marked `requires_approval=True` ends the run with `DeferredToolRequests`, and the serialised conversation "is everything you need to resume" in a new process ([Deferred tools](https://pydantic.dev/docs/ai/tools-toolsets/deferred-tools/)). It also has co-maintained durable-execution adapters for Temporal, DBOS, Prefect and Restate ([Durable execution](https://pydantic.dev/docs/ai/integrations/durable_execution/overview/)). The risk is churn. **v2.0.0 shipped on 23 June 2026 and reached v2.57.0 by 16 October**, roughly one minor release a day ([pydantic-ai releases](https://github.com/pydantic/pydantic-ai/releases/tag/v2.0.0)). So pin it and keep it behind your own `AgentRunner` interface. The **OpenAI Agents SDK** is the natural second backend: `RunState.to_json()` / `from_json()` is the cleanest cross-process resume primitive found, but the SDK is still 0.x and OpenAI-first ([HITL docs](https://openai.github.io/openai-agents-python/human_in_the_loop/)). **LangGraph** is the off-the-shelf choice if you would rather not write the state machine, at the cost of LangChain's abstraction weight. **Microsoft Agent Framework** has a `FileCheckpointStorage` that maps almost one-to-one onto a local run folder, but its checkpoints are pickled, and the docs warn "never load checkpoints from untrusted or potentially tampered sources" ([MAF checkpoints](https://learn.microsoft.com/en-us/agent-framework/workflows/checkpoints)). AutoGen is in maintenance mode, and its own README sends new users to MAF ([AutoGen](https://github.com/microsoft/autogen)).

Gates are coarse pause points between steps, so v1 needs no durable-execution engine. A gate persists `run.json` (pipeline cursor, loop counters, budget ledger), writes the handoff and exits; `resume` reloads it. Every step should still be idempotent from day one. ADK warns that tools run "at least once" ([ADK resume](https://adk.dev/runtime/resume/)), and LangGraph nodes re-execute from their start on resume ([LangGraph interrupts](https://docs.langchain.com/oss/python/langgraph/interrupts)), so git commits and PR creation need idempotency keys whatever engine comes later. When CI and webhooks arrive, **DBOS** is the best engine to grow into. It is MIT, an embedded library with "no separate queueing service or message broker — just Postgres", and it has first-party Pydantic AI support ([dbos-transact-py](https://github.com/dbos-inc/dbos-transact-py)). Its SQLite mode exists in source but is not documented in the README ([_sys_db_sqlite.py](https://github.com/dbos-inc/dbos-transact-py/blob/main/dbos/_sys_db_sqlite.py)).

No orchestration framework detects repetition, only count caps, so stuck-loop detection is a port. **OpenHands' `StuckDetector`** (MIT) checks five patterns over the last 20 events: repeated action/observation, repeated action/error, monologue, ping-pong alternation and context-window error loops. Its defaults are 4+ identical pairs, 3+ error repeats, 3+ monologue messages and 6+ alternating cycles ([stuck_detector.py](https://github.com/OpenHands/software-agent-sdk/blob/main/openhands-sdk/openhands/sdk/conversation/stuck_detector.py), [guide](https://github.com/OpenHands/docs/blob/main/sdk/guides/agent-stuck-detector.mdx)). Port it inside each agent, and add your own check between loop iterations. If iteration N's review findings match those of N−2, or the developer's diff comes back empty, escalate to a human gate before `max_iterations` runs out.

### Definitions, layering and handoffs: no library locks fields, so the policy file does

**No mainstream Python config library implements "org-locked fields cannot be overridden by lower layers"**. Dynaconf, Hydra, pydantic-settings and deepmerge all just override in load order. OmegaConf has a read-only flag, but merging into a read-only node is undocumented ([OmegaConf docs](https://omegaconf.readthedocs.io/en/2.3_branch/usage.html)). dature offers per-field merge rules and source tracing but is young ([dature comparison](https://dature.readthedocs.io/en/latest/comparison/why-not-dynaconf/)). The cleaner design is to keep restricted fields out of the merge entirely. The org policy file is the only source for the tier → model map, providers, tool allow-lists and budgets. Agent and pipeline files may only *request* a tier or a tool, and preflight rejects requests that break policy with a provenance-bearing error rather than silently clamping them. Repo-controllable sections (instructions, schemas, pipeline shape) deep-merge with BMAD's documented rules: "scalars override, tables deep-merge, arrays of tables keyed by `code` or `id` replace matching entries ... all other arrays append" ([BMAD architect SKILL.md](https://github.com/bmad-code-org/BMAD-METHOD/blob/V6.12/src/bmm-skills/agents/bmad-agent-architect/SKILL.md)). Claude Code is useful prior art for precedence: managed (org) settings beat the CLI flag, which beats project, which beats user ([Claude Code subagents](https://code.claude.com/docs/en/sub-agents)). The admin rules in v1 are lookups and arithmetic, so a Pydantic `OrgPolicy` plus about 150 lines of checks is enough. Put it behind a `PolicyDecider` interface so that Cedar via `cedarpy` can replace it later. That binding is in-process with Windows wheels but is "not officially supported by AWS or the Cedar Policy team" and has a single maintainer ([cedarpy](https://pypi.org/project/cedarpy/)).

For the agent file, the de facto format is Markdown + YAML front matter. The Claude Code subagent schema is the most detailed version: `name`, `description`, `tools`, `disallowedTools`, `model`, `permissionMode`, `maxTurns`, `skills`, `mcpServers`, `effort` and `isolation` ([Claude Code subagents](https://code.claude.com/docs/en/sub-agents)). Adopt those field names and add `tier`, `temperature`, `input_schema` and `output_schema`, borrowing goose's recipe fields for structured output (`response.json_schema`) and retry checks (`retry.checks`, `on_failure`) ([goose recipe reference](https://goose-docs.ai/docs/guides/recipes/recipe-reference)). Claude Code silently ignores unknown fields. Yours should fail on them, because governance needs typo detection. Oracle's Open Agent Spec is the only formal, conformance-tested neutral spec, and it suits a later `export` target rather than authoring ([oracle/agent-spec](https://github.com/oracle/agent-spec)). Handoffs use python-frontmatter plus a framework envelope (`run_id`, `step_id`, `from_agent`, `to_agent`, `status`, `cost`), with a `payload` validated against the producing agent's Pydantic `output_schema`. No library checks that step N's output schema satisfies step N+1's input, so that check is roughly 50-100 lines over `model_json_schema()`. Seed the body templates from spec-kit (constitution → specify → plan → tasks → implement) and OpenSpec's brownfield-friendly change folders with `ADDED`/`MODIFIED` SHALL requirements ([spec-kit](https://github.com/github/spec-kit), [OpenSpec](https://github.com/Fission-AI/OpenSpec)).

### Model calls: one httpx transport makes TokenLean metering framework-independent

**No agent framework surfaces HTTP headers from successful responses.** Pydantic AI reads them only when mapping errors ([models/openai.py](https://github.com/pydantic/pydantic-ai/blob/main/pydantic_ai_slim/pydantic_ai/models/openai.py)), and the OpenAI Agents SDK not at all ([openai_responses.py](https://github.com/openai/openai-agents-python/blob/main/src/agents/models/openai_responses.py)). LangChain's `ChatOpenAI(include_response_headers=True)` is the one exception ([LangChain response metadata](https://python.langchain.com/docs/how_to/response_metadata)). Cost capture is therefore glue code whichever loop library you pick, and the right place for it is below the framework. openai-python supports a custom `base_url`, per-request `extra_headers`, `.with_raw_response`, and a swappable httpx client with "event hooks" ([openai-python](https://github.com/openai/openai-python)). Build one `httpx.AsyncClient` per run. Its request hook reads a `ContextVar` holding agent, pipeline, step, team, run and parent-agent identity and sets the headers; its response hook parses `x-tokenlean-*` cost headers into the run's budget ledger. Inject that client into `AsyncOpenAI` and `AsyncAnthropic`, then into Pydantic AI's providers. Avoid LiteLLM here. It would be a second router behind TokenLean, its SDK-side response-header access is "currently only supported for openai", and its `enterprise/` directory carries a separate licence ([LiteLLM response headers](https://docs.litellm.ai/docs/proxy/response_headers), [litellm LICENSE](https://github.com/BerriAI/litellm)).

### Execution: governed backends, worktrees, and an OS sandbox as the real boundary

**Claude Code and Codex CLI are the most governable external backends.** Claude Code has `claude -p --output-format json --json-schema`, which returns `structured_output` plus `total_cost_usd`. `--bare` skips repo hooks, plugins and MCP servers, which `-p` otherwise runs "even in a folder you've never trusted", and `--permission-mode dontAsk` denies anything that would prompt ([Claude Code headless](https://code.claude.com/docs/en/headless)). A managed `allowedProviders: ["customEndpoint"]` with `ANTHROPIC_BASE_URL` makes the gateway the only allowed destination. Anthropic "doesn't support routing Claude Code to non-Claude models through any gateway" ([Claude Code LLM gateway](https://code.claude.com/docs/en/llm-gateway)). Prefer the MIT `claude-agent-sdk`, which offers typed messages and Python `PreToolUse` hooks for shell policy, but note that the CLI it bundles is proprietary ([claude-agent-sdk-python](https://github.com/anthropics/claude-agent-sdk-python)). `codex exec --json --output-schema` emits a JSONL event stream with token usage. Its sandbox defaults to read-only, `--full-auto` "is no longer supported", and `--ignore-user-config` stops personal config from changing model or proxy ([Codex non-interactive](https://learn.chatgpt.com/docs/non-interactive-mode)). Codex reaches a proxy through a `[model_providers.X]` block with `wire_api = "responses"` ([LiteLLM Codex docs](https://docs.litellm.ai/docs/proxy/client_setup/codex_cli.md)).

For the long tail, **ACP** (Zed's Agent Client Protocol) is the only protocol built to drive local coding agents. About 43 agents speak it natively or through adapters, including Gemini CLI, Copilot CLI, Goose, OpenCode, OpenHands, and Claude and Codex via third-party adapters ([ACP agents](https://agentclientprotocol.com/overview/agents)). It has an Apache-2.0 Python SDK with Pydantic models ([python-sdk](https://github.com/agentclientprotocol/python-sdk)). ACP standardises sessions, streaming and permission requests, but not model selection, base URL, structured results or cost, so each backend still needs a launch profile. ACP's permission callbacks give you a second, uniform enforcement point for tool allow-lists. Treat Gemini CLI as replaceable: its docs say it "was replaced by Antigravity CLI on June 18th, 2026" for unpaid and Google One users ([Gemini CLI headless](https://geminicli.com/docs/cli/headless/)). Remote agents (Devin, Jules, Copilot coding agent) bypass both TokenLean and your sandbox entirely. Gate them by repo allow-list and a mandatory Review step. Devin's v3 API is the richest of the three, with `structured_output_schema` and `max_acu_limit` ([Devin API](https://docs.devin.ai/api-reference/v3/sessions/post-organizations-sessions.md)).

No single OSS sandbox isolates strongly on all three operating systems, so layer it. The **worktree per step** is the diff and rollback unit, but it provides no security. Drive plain `git worktree` from Python rather than adding Worktrunk or copying the AGPL claude-squad. The **OS process sandbox** is Anthropic's `srt` (Apache-2.0, beta). It uses Seatbelt on macOS and bubblewrap plus a network namespace on Linux, its Windows support is **alpha** and needs one-time elevated setup, and network egress goes through a domain allow-list proxy ([sandbox-runtime](https://github.com/anthropic-experimental/sandbox-runtime)). Claude Code's own sandbox "runs on macOS, Linux, and WSL2. On native Windows, Claude Code runs commands unsandboxed", and `sandbox.failIfUnavailable: true` turns that into a startup failure ([Claude Code sandboxing](https://code.claude.com/docs/en/sandboxing)). Codex has native Windows modes (`mxc` recommended, plus `elevated` and `unelevated`), which admins can constrain via `requirements.toml` ([Codex Windows sandbox](https://learn.chatgpt.com/docs/windows/windows-sandbox)). CI gets an ephemeral container per step, with egress limited to TokenLean and package mirrors. Self-hosted E2B (Apache-2.0, Firecracker) is the central microVM pool at 1,000-developer scale, though GCP is its only mature target ([E2B open source](https://e2b.dev/open-source)). Command allow-lists remain advisory, because prefix rules are bypassable via `bash -c`, `python -c` or pipes. Define one framework policy schema modelled on Codex's Starlark `prefix_rule` (allow/prompt/forbidden, strictest wins) and compile it into Claude permission rules, Codex `.rules` and Copilot `--allow-tool` filters ([execpolicy write-up](https://codex.danielvaughan.com/2026/05/21/codex-cli-execution-policy-rules-starlark-command-governance-enterprise-allowlists/)).

### Code understanding and memory: test-aware blast radius from an MIT graph

Every persistent code graph with blast-radius support is built on tree-sitter, so cross-file resolution is heuristic. Present impact lists as *candidate* sets that the Review and QA agents confirm, never as ground truth. **code-review-graph** (MIT, pip-installable, SQLite) is the primary choice. Its impact tool traces "every caller, dependent and test" with test-coverage edges and incremental SHA-256 re-parsing, though it admits conservative over-approximation and a circular recall evaluation ([code-review-graph](https://github.com/tirth8205/code-review-graph)). **codebase-memory-mcp** (MIT, single C binary, 162 languages, official Windows binary) is the fallback for large or Windows-heavy repos. It reports indexing the Linux kernel in about three minutes (self-published), and its `detect_changes` maps a git diff to affected symbols ([codebase-memory-mcp](https://github.com/DeusData/codebase-memory-mcp)). A 31-repo preprint found its graph agent scored **83% answer quality against 92% for file exploration, at 10x fewer tokens** ([arXiv 2603.27277](https://arxiv.org/html/2603.27277v1)), which argues for graph-as-accelerator rather than graph-as-oracle. **Graphify** (Apache-2.0) is real and popular but pre-1.0, shipping about two releases a day. Its impact tools work at PR and community level, with no dependents or tests tool, and a wrong-language parse "fails silently" ([Graphify](https://github.com/Graphify-Labs/graphify), [MCP tools](https://docs.graphify.com/reference/mcp-tools)). Keep it as an optional orientation map for the Design agent. multilspy (MIT) provides precise references for Java DI and TypeScript type-driven calls, and pytest-testmon (MIT) confirms affected Python tests dynamically ([multilspy](https://github.com/microsoft/multilspy), [pytest-testmon](https://pypi.org/project/pytest-testmon/)).

For repo memory, **AGENTS.md** is the cross-tool standard, stewarded by the Linux Foundation's Agentic AI Foundation and used by "over 60k open-source projects" by its own count ([agents.md](https://agents.md/)). Claude Code reads it natively from v2.1.277 when no CLAUDE.md exists ([Claude Code memory](https://code.claude.com/docs/en/memory)). Use `@AGENTS.md` imports rather than symlinks, which need admin rights or Developer Mode on Windows. When learned memory arrives, **Mem0** (Apache-2.0) uses Qdrant as its default vector store, so it can point at TokenLean's existing instance with per-repo namespaces ([Mem0 vector DBs](https://docs.mem0.ai/components/vectordbs/overview)).

### Observability and surfaces: emit agent spans, let the proxy own LLM spans

Emit plain OpenTelemetry with the GenAI conventions: a `run` root span with `session.id = run_id`, `invoke_agent {agent}` per step, and `execute_tool` children. Propagate W3C `traceparent` to TokenLean so its spans become children of your step spans. Every `gen_ai.*` attribute is still "Development" status in the new `semantic-conventions-genai` repo (schema `gen-ai/1.42.0`), so pin the schema and isolate attribute names in one module ([Dash0 explainer](https://www.dash0.com/knowledge/opentelemetry-genai-semantic-conventions-explained)). If TokenLean already emits LLM-call spans with token and cost data, do not duplicate them, or cost gets double-counted. Langfuse accepts OTLP and maps `gen_ai.*`, provided `session.id` and `user.id` are on every span ([Langfuse OTel](https://langfuse.com/docs/opentelemetry/introduction)). Avoid the Logfire *platform*: the SDK is MIT, but the backend is closed and self-hosting needs an enterprise licence ([Logfire FAQ](https://logfire.pydantic.dev/docs/faq)). The CLI is Typer (MIT) or Cyclopts (Apache-2.0, better for Pydantic-typed parameters, Python ≥ 3.11) ([cyclopts](https://github.com/BrianPugh/cyclopts)). The human gate is Rich rendering, a questionary approve/edit/reject/comment prompt and `click.edit()` on the handoff file, followed by re-validation, and that same gate abstraction later maps onto a PR comment, a web UI or VS Code.

## The custom glue is governance, budgets and adapters, not orchestration

Once the reuse choices are made, what remains is narrow and almost all of it is where your product differs. You write the **pipeline state machine** (steps, gates, bounded loops, a `when` evaluator over handoff front matter, overlays) and the **run-folder checkpointing** (atomic `run.json`, persist-and-exit gates, cross-process resume, versioned state). You write the **layered loader** that merges repo-controllable fields with BMAD semantics and records provenance, and the **preflight `PolicyDecider`** that validates tier, model, provider, tools and remaining budget against the org policy. The **template compiler** turns Markdown agent files into Pydantic AI AgentSpecs plus registered Python tools. The **handoff contract** layer adds the envelope, per-agent payload validation with retries, and step-to-step schema compatibility. The **TokenLean transport** handles identity headers, cost harvesting and budget enforcement. **Child-agent spawning** enforces depth limits, tool subsets of the parent and budget slices from the parent ledger. You also need the **stuck-detector port** with inter-iteration oscillation checks, an **`AgentBackend` protocol** with Claude SDK, Codex and ACP implementations and per-version contract tests, a **policy compiler** from one shell-rule schema into each backend's native format, the **worktree/diff/rollback** lifecycle and sandbox selection, a **`CodeIndex` port**, the **OTel span model** with a local `trace.jsonl`, and a **publisher** that replays runs to the central store. The governance research put the merger at about 200 lines, preflight at about 150 and schema compatibility at about 100. These are estimates, not measurements, but they show the true build is small and concentrated.

## Conclusion

The research changes the build-vs-adopt question. The hard part of an agentic SDLC framework is no longer orchestration. Pipeline DSLs, sub-agent formats, sandboxes, ACP backends and code graphs all exist under permissive licences, and Archon has already designed the node vocabulary you need. What nobody has built is *governance at the call path*: one proxy that every model call passes through, an org policy that lower layers can request against but never override, and budgets that narrow from tenant to team to run to child agent. That puts the centre of gravity of this project as much in TokenLean as in the new Python framework. Multi-format endpoints, streamed cost reporting, `traceparent`, team scope and hierarchical budgets are prerequisites, not nice-to-haves, and they should be scheduled alongside the framework's first sprint rather than after it.

The second implication is defensive. Most of the reusable pieces are moving fast: Pydantic AI ships almost daily, Graphify twice a day, agent CLIs drop flags between releases, and the GenAI telemetry conventions are explicitly unstable. A framework that wraps each of them behind its own narrow interface (`AgentRunner`, `AgentBackend`, `PolicyDecider`, `CodeIndex`, a single telemetry-attribute module), pins versions, and runs contract tests per backend will outlast any individual choice in the stack table. One that couples directly to them will spend its maintenance budget chasing upstream churn.
